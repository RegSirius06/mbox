# QUIC TLS: доверие и ротация сертификатов

**Автоматически не устанавливается и на VPS не запускается.** В beta.4 `quic_ca_pem` является доверенным X.509 сертификатом в `quic-go`; стандартно проверяются цепочка, дата и IP SAN. Для IPv4 endpoint нужен `subjectAltName=IP:<адрес>`, не только DNS SAN. Если старый профиль содержит самоподписанный *leaf* сертификат, его замена потребует однократной миграции доверия.

## Создание доверенного CA

На **изолированной доверенной машине** создайте собственный P-256 CA примерно на 3 года:

```bash
umask 077
openssl req -new -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -days 1095 -sha256 -subj '/CN=MBox QUIC dedicated CA' \
  -addext 'basicConstraints=critical,CA:TRUE' \
  -addext 'keyUsage=critical,keyCertSign,cRLSign' \
  -keyout ca.key -out ca.crt
```

В профиль передаётся **только публичный** `ca.crt` как `quic_ca_pem`. Никогда не записывайте `ca.key` в Git, APK, mbox://, shared hosting или логи.

Для полной автономной ротации `tools/quic-cert-renew.sh` требует закрытый CA-ключ **на VPS** в `/etc/mbox/quic/ca.key`, 0600 root-only. При компрометации root злоумышленник сможет выпускать доверенные сертификаты до конца действия CA. Это существенный риск. Более безопасный вариант — хранить CA офлайн и выпускать leaf вручную/через отдельный доверенный сервис подписи, не включая таймер.

## Настройка на VPS — только после согласия владельца

Резервируйте старые файлы и unit; сначала проверьте схему на staging. Установите `ca.crt` и (только если принимаете риск) `ca.key` в `/etc/mbox/quic/`; `ca.key` 0600, каталоги root:mbox 0750. Скрипт `tools/quic-cert-renew.sh` разместите в `/usr/local/libexec/mbox-quic-cert-renew` с правом исполнения. В реальном systemd unit укажите для шлюза **пару** `--cert /etc/mbox/quic/current/server.crt --key /etc/mbox/quic/current/server.key`: симлинк на поколение меняется атомарно.

Пример `/etc/mbox/quic/renew.env` (0640, владелец root):

```ini
MBOX_QUIC_ENDPOINT_IP=203.0.113.10
MBOX_QUIC_UNIT=mbox-native-quic.service
MBOX_QUIC_READ_GROUP=mbox
MBOX_QUIC_LEAF_DAYS=60
MBOX_QUIC_RENEW_BEFORE_DAYS=14
```

`203.0.113.10` — **только пример**, замените на свой IPv4. Проверьте имя настоящего systemd unit. Установите `deploy/systemd/mbox-quic-renew.{service,timer}` в `/etc/systemd/system/`, выполните `systemctl daemon-reload`, `systemctl start mbox-quic-renew.service`. **До включения таймера** проверьте сертификат и IP SAN через изолированный QUIC-клиент. После успешной проверки можно выполнить `systemctl enable --now mbox-quic-renew.timer`. Проверка — раз в день, выпуск за 14 дней до окончания, leaf на 60 дней. Скрипт создаёт новое поколение, проверяет ключ/цепочку/IP SAN, атомарно обновляет симлинк и перезапускает gateway; при неудаче откатывает симлинк и пытается вернуть старый gateway. Контролируйте `journalctl -u mbox-quic-renew.service` и фактическое время истечения. Запуск systemd сам по себе не доказывает, что QUIC работает.

## Однократная миграция старых профилей

Сертификат старого тестового QUIC истекает **7 декабря 2026 года**. Нельзя просто принять чужой новый сертификат после истечения старого. По уже аутентифицированному каналу оператора/HTTPS+Noise доставьте пользователям новый `mbox://` со старой учётной записью, прежним `quic_url` и **публичным CA** в `quic_ca_pem`; пользователь явно импортирует профиль, проверяет QUIC и только потом отказывается от старого доверия. Можно использовать временный параллельный QUIC тестовый порт для плавного перехода. HTTPS-only профили остаются прежними. Автоматического переноса доверия сейчас **нет**.

## Обязательные проверки

В staging последовательно испытать правильный сертификат, просроченный, чужой CA, неправильный IP SAN, новый leaf с тем же CA, ошибку выпуска, откат после неудачного рестарта, восстановление и миграцию профиля. Отмечать успешными только фактически проверенные пункты. Никогда не использовать InsecureSkipVerify.
