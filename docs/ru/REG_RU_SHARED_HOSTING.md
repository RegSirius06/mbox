## Что именно покупать

В проверенной топологии публичный frontend — **виртуальный/shared hosting REG.RU**, а не VPS. На нём лежат обычный сайт и FastCGI relay. Origin MBox и конечный exit могут находиться на других серверах/в других странах.

```text
телефон -> HTTPS -> REG.RU shared hosting -> FastCGI -> MBox origin -> sing-box -> exit
```

Для нового развёртывания разумно выбирать нормальный тариф из скоростной линейки (`Хост-0`, `Хост-1`, `Хост-3` по текущей справке REG.RU), а не самый дешёвый тариф, рассчитанный на простые статические страницы. Нам важны нормальные динамические/FastCGI ресурсы и скорость обработки запросов, а не объём диска.

REG.RU сейчас заявляет безлимитный трафик на тарифах виртуального хостинга. Это удобно по сравнению со схемами, где CDN тарифицирует/ограничивает egress по объёму, но «безлимит» всё равно подчиняется fair-use, ограничениям нагрузки и договору провайдера.

**Проверьте условия использования.** В актуальной справке REG.RU proxy-сервисы указаны среди запрещённых сценариев shared hosting. MBox документирует технически проверенную схему, но не даёт разрешения нарушать условия провайдера. Используйте её только если ваш конкретный сценарий разрешён действующими правилами/поддержкой.

## Идентификация

Для владельца услуги хостинга действует процедура идентификации. Проходите её на реальные данные. Для `.ru/.рф/.su` с 1 сентября 2026 действует отдельное обязательное подтверждение администратора через ЕСИА при регистрации/продлении.

Сам домен необязательно регистрировать у REG.RU, чтобы направить его на shared hosting REG.RU, но правила регистратора/реестра/провайдера всё равно действуют.

## Почему вообще обсуждается `.ru`

Исторически `.fun` frontend этой схемы проходил в ограниченном мобильном интернете MTS/T2, а на MegaFon мог не открываться даже обычным браузером. Значит, по крайней мере один MegaFon failure mode лежит до MBox/Noise.

Поэтому следующий тест — дать одному backend два hostname: `.fun` и `.ru`. Если на одном и том же IP/backend `.ru` открывается, а `.fun` нет, сильнее становится гипотеза про SNI/domain category/allow-list. Гарантий нет.

## Развёртывание relay

```bash
sudo mboxctl relay bundle
sudo mboxctl relay paths
```

Безопасный RC1-deploy по SSH подробно описан в
[`../SAFE_SSH_RELAY_DEPLOY.md`](../SAFE_SSH_RELAY_DEPLOY.md). Команда требует
явно указать `--remote-private-dir` вне webroot, `--origin-config` работающего
origin, `--relay-binary` с проверенной контрольной суммой и поддерживает
`--dry-run`. Пример:

```bash
sudo mboxctl relay deploy \
  --ssh USER@HOST \
  --remote-dir /var/www/USER/data/www/front.example.com \
  --remote-private-dir /var/www/USER/data/mbox-stage-private \
  --origin-config /etc/mbox-stage/server.json \
  --relay-binary /root/mbox-relay-compat.fcgi \
  --relay-sha256 EXPECTED_SHA256 \
  --dry-run
```

После проверки удалите только `--dry-run`. В случае ошибки HTTP health
деплой автоматически восстанавливает прошлую версию; есть отдельная команда
`mboxctl relay rollback`. FTPS в HMAC-версии намеренно запрещён: он может
поместить секрет в публичный webroot. Обычный deploy не затрагивает
`index.html`, `404.html` и `.htaccess`; параметр `--site` меняет только
декоративные страницы по явному запросу.

Проверка:

```bash
sudo mboxctl relay test
```

Неавторизованный probe обычно получает обычный 404. Для определения слоя блокировки используйте `mbox-netprobe` и [операторский тест](OPERATOR_TEST.md).
