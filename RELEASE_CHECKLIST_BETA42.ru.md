# Проверка перед публикацией MBox beta.4.2

1. **Исходники.** На Arch сверить файловые изменения с VPS и перенести только проверенные Python/HTML-исходники. Не переносить в Git `mbox.conf` с секретами, базу пользователей, токены, private keys и release keystore.
2. **Версии.** `VERSION=1.0.0-beta.4.2`, Android `versionCode=9`, `versionName=1.0.0-beta.4.2`, согласованы сборочный и проверочный скрипты. Нельзя случайно опубликовать старую APK под новым тегом.
3. **Тесты.** `git diff --check`, полный `pytest`, Go tests, Gradle release, необходимые CI и secret scan. Результаты зафиксировать для последнего коммита.
4. **Подпись.** Собрать релиз существующим ключом, проверить cert SHA-256 pinned signer и `tools/check-production-apk.sh`. Сверить SHA-256 именно итогового файла, предназначенного для загрузки.
5. **Реальный Android.** Обновить приложение без удаления данных, импортировать HTTPS-подписку, проверить актуальный QUIC/HTTPS, старый прямой HTTPS, кэш/обновление подписки и поведение после отсутствия сети. Отдельно записать неудачу старого QUIC; не объявлять её изменением MBox wire protocol без доказательства.
6. **Панель.** Проверить вход, пользователя, постоянную ссылку, отзыв, редактирование и проверку конфига. Для чистой установки протестировать systemd права на бэкапы и Caddy, а не полагаться на ручной override, выполненный на текущем VPS.
7. **Документы.** Отдельно на RU и EN: `README`, `CHANGELOG`, `RELEASE_NOTES` и status. Не писать «все команды `mboxctl` реализованы в панели», пока это не доказано.
8. **Релиз.** Закоммитить и запушить всё, дождаться зелёного CI на том же SHA, создать тег `v1.0.0-beta.4.2` и GitHub **Prerelease**, приложить подписанный APK и `.sha256`. Публиковать только после тестирования точного итогового файла.
9. **Оставшиеся ограничения.** QR/UX, 2 × 2 ingress, traffic/device quotas, fail-closed leak capture, Lockdown, soak, QUIC certificate rotation — открытые задачи для дальнейшей beta/RC, их нельзя выдавать за готовые.
